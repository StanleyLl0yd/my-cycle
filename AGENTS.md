# AGENTS.md

## Область действия

Эти правила действуют для всего репозитория и обязательны при полном аудите, cleanup, оптимизации или глубоком рефакторинге проекта.

## Главный принцип

Цель рефакторинга — максимально упростить, сократить и очистить кодовую базу при сохранении 100% текущей функциональности, поведения приложения, UI/UX, публичных интерфейсов и заявленных возможностей.

Не гнаться за минимальным количеством строк любой ценой. Цель — минимальная необходимая сложность проекта, а не code golf.

При любом сомнении между «оставить рабочий код» и «удалить код, потому что он кажется лишним» сохранять рабочий код, пока не доказано, что он действительно не нужен.

Если изменение только делает код другим, но не делает его объективно проще, безопаснее, понятнее или эффективнее, не вносить такое изменение.

## Обязательный полный аудит

Перед рефакторингом изучить весь репозиторий, а не только недавно изменённые или очевидные файлы:

- production source code;
- tests;
- resources;
- build scripts;
- dependency declarations;
- CI/CD;
- static-analysis/security configuration;
- store/release tooling;
- documentation;
- directory structure.

Сначала определить фактическую архитектуру, существующие пользовательские функции и реальные контракты приложения. Затем сформировать внутренний список кандидатов на удаление, объединение, упрощение и оптимизацию.

## Что необходимо искать и удалять

Проверять весь проект на наличие:

- мёртвого и недостижимого кода;
- неиспользуемых функций, классов, методов, переменных, констант, типов, интерфейсов и импортов;
- legacy-кода, который больше не участвует в работе приложения;
- временных workaround'ов, которые больше не нужны;
- дублирующегося или почти дублирующегося кода;
- ненужных abstraction layers;
- лишних wrapper/helper-функций;
- лишних преобразований данных;
- повторной валидации уже валидированных данных;
- defensive checks, если соответствующее состояние уже гарантировано типами, архитектурой или предыдущей проверкой;
- повторных проверок одного и того же условия;
- избыточных fallback'ов;
- неиспользуемых зависимостей;
- устаревших конфигурационных параметров;
- ненужных feature flags;
- закомментированного старого кода;
- неактуальных TODO/FIXME;
- лишних файлов и ресурсов.

Особое внимание уделять конструкциям вида повторных `null`/state checks, лишним `try/catch`, цепочкам wrapper → wrapper → wrapper, ненужным DTO/model conversions, промежуточным состояниям, compatibility branches и остаткам предыдущих рефакторингов.

## Что необходимо упрощать

Искать места, где код можно безопасно:

- сделать короче без потери читаемости;
- сделать проще;
- объединить;
- заменить стандартными средствами языка/framework/library;
- избавить от лишних промежуточных объектов и состояний;
- избавить от лишних циклов, проходов, копирований и преобразований;
- упростить control flow;
- уменьшить количество состояний и ветвлений;
- уменьшить связность компонентов;
- устранить повторяющуюся бизнес-логику;
- централизовать действительно общую логику, только если это уменьшает общий объём и сложность кода.

Не вводить новую abstraction только ради формального DRY, если результат становится сложнее для понимания или сопровождения.

## Архитектура

Проверять:

- нет ли компонентов или слоёв, существующих только исторически;
- нет ли чрезмерной абстракции;
- нет ли классов или модулей, которые можно безопасно удалить или объединить;
- нет ли преждевременной универсализации;
- нет ли архитектуры «на будущее», которая сейчас не даёт пользы;
- соответствует ли сложность решения фактической сложности задачи.

Не выполнять крупный rewrite только потому, что другая архитектура кажется красивее или современнее.

## Производительность

Оптимизировать только там, где есть практический смысл. Проверять:

- лишние вычисления;
- повторные запросы;
- ненужные allocations;
- лишние re-render/rebuild/recompute;
- повторное чтение или преобразование одних и тех же данных;
- неэффективные структуры данных;
- операции, которые можно выполнить один раз вместо многократного выполнения.

Не делать микрооптимизации, которые ухудшают читаемость и не дают измеримого или очевидного выигрыша.

## Зависимости

Для каждой dependency проверять фактическое использование.

- Удалять неиспользуемые зависимости.
- Выявлять библиотеки с дублирующим назначением.
- Допускается заменить dependency стандартным или очень небольшим собственным кодом, только если это объективно уменьшает сложность проекта.
- Не заменять хорошо поддерживаемую библиотеку самописным кодом без веской причины.

## Критическое ограничение: никаких функциональных регрессий

После рефакторинга приложение должно вести себя так же, как до него.

Нельзя без абсолютной необходимости:

- удалять пользовательские функции;
- менять существующий UX;
- менять бизнес-логику;
- менять публичные API или контракты;
- менять форматы данных;
- менять поведение edge cases;
- уменьшать функциональность ради сокращения кода;
- добавлять новые функции, не относящиеся к задаче;
- усложнять архитектуру ради «best practices».

Сохранять application identity, persistence contracts, release/signing contracts и platform-specific behavior, если задача явно не требует их изменения.

## Проверка перед удалением

Не считать код мёртвым только потому, что обычный textual search не нашёл прямого вызова.

Перед удалением убедиться, что код не используется:

- напрямую;
- косвенно;
- через callbacks/events;
- через reflection или dynamic loading;
- через framework conventions;
- через manifests/resources/configuration;
- через build system;
- через CI/CD или release tooling;
- через platform-specific code;
- только в тестах или debug tooling, если это tooling всё ещё требуется.

## Порядок внесения изменений

1. Изучить весь репозиторий и определить фактическое поведение.
2. Сформировать внутренний список кандидатов на удаление, объединение, упрощение и оптимизацию.
3. Вносить изменения небольшими логическими группами.
4. После каждой значимой группы запускать доступные project-specific проверки: tests, lint, build, static analysis и другие обязательные проверки проекта.
5. Если тестового покрытия недостаточно для безопасного изменения критической логики, сначала добавить минимальные regression tests, фиксирующие текущее поведение.
6. После завершения выполнить полный финальный clean build, test suite, lint, static analysis и остальные доступные проверки проекта.
7. После первого завершённого рефакторинга обязательно выполнить второй проход по уже изменённому проекту и снова искать dead code, duplication, лишние abstractions, проверки, зависимости и legacy.

Не ограничиваться рекомендациями: безопасные подтверждённые улучшения следует вносить непосредственно в проект.

## Комментарии

Соблюдать существующее правило проекта:

- комментариев должно быть минимум;
- комментарии допустимы только там, где объясняют неочевидную причину решения, ограничение или важный контракт;
- не добавлять комментарии, пересказывающие очевидный код;
- удалять устаревшие и бесполезные комментарии;
- комментарии в исходном коде должны быть только на английском;
- не оставлять TODO/FIXME вместо завершения задачи, если они не являются действительно необходимым и актуальным ограничением проекта.

## Финальный отчёт после полного аудита/refactoring

Отчёт должен содержать:

1. Что было удалено.
2. Что было объединено.
3. Что было упрощено.
4. Какие зависимости были удалены.
5. Какие потенциальные legacy-компоненты обнаружены.
6. Какие места намеренно не изменены и почему.
7. Какие tests/build/lint/static-analysis/project-specific проверки выполнены и с каким результатом.
8. Какие области нельзя было безопасно оптимизировать без дополнительной информации или тестов.
9. Достоверную статистику до/после, если её можно получить:
   - количество файлов;
   - строки исходного кода;
   - количество зависимостей;
   - количество тестов;
   - размер production/build artifact, если применимо.

Не придумывать статистику и не выдавать неполные проверки за успешно выполненные.

## Итоговая цель

После полного аудита проект должен содержать максимально маленькую, чистую, понятную и эффективную кодовую базу, в которой остаётся только код, действительно необходимый для текущей функциональности, без функциональных регрессий и без искусственного усложнения.
